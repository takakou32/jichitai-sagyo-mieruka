# 説明：移行の実施（下書き）

> 〔要確認〕は推測で書いた箇所。直したら印を外す。

| 項目 | 内容 |
|---|---|
| 大きな枠 | 切替 |
| 目的 | 移行ツールを手順書どおりに実行し、本番環境に移行データを作る |
| 種類 | リハーサル（全体移行テストを含む）／本番切替 |
| 時期・頻度 | 団体（グループ）ごと。リハーサルは本番の前に複数回、本番切替は1回。対象団体と日程は切替スケジュール（別資料）を参照 |
| きっかけ | 切替スケジュールで日程が確定する |
| 完了の条件 | リハーサル：結果と課題が記録され、「移行の準備」に渡されている。本番切替：Go判定が出て、稼働日に業務を始められる状態になる |

## リハーサルと本番切替の違い

対象の環境（本番環境）、作業の段取り、Go/No-Go判定をする人は同じ。違うのは次の点だけ。

| 違い | リハーサル | 本番切替 |
|---|---|---|
| 目的 | 手順書を検証し、**完成させる** | 完成した手順書を**正確に実行する**。本番で手順を工夫したり、変えたりはしない |
| 実施日 | 土日。または平日に時間をずらして、土日と同じ段取りで行う（全体移行テスト） | 閉庁日（土日祝）の数日間 |
| 結果の扱い | 課題を「移行の準備」へ戻し、手順書に反映する。データは「移行結果の確認」の本確認に使う | 稼働する。移行結果の最終確認を支援する |

- リハーサルは、手順書だけでなく、判断と連絡の段取りを試す場でもある。本番と同じ形で回して、穴を本番の前に見つける。
- リハーサル後の環境の初期化は、本番切替の全体手順に含まれている。

## 始める前にそろっていること

- 前回のリハーサルの課題が、「移行の準備」で手順書に反映されていること
- 切替手順書・タイムチャートが最終版であること
- 移行ツールと移行資産が最終版であること
- 当日の要員・連絡先が決まっていること

## 関わる人

リハーサルも本番切替も、団体ごとに確認者と作業者が組になって進める。チームとして当日のリーダーは立てない。

| 誰が | 何をするか |
|---|---|
| 確認者（センター） | タイムチャートの進行に合わせて、作業者に作業の開始を指示する。アップロードされたログとDBで、エラーと件数を確認する |
| 作業者（自チーム） | 確認者の指示を受けて、手順書どおりに移行ツールを実行し、ログを格納する |
| 移行チーム | 住記などの移行ツールを実行する（10数人規模。多数の業務の実行順序をハンドリングするため、当日はこちらに移管している） |
| センター | 致命的なエラーかどうかの判断、Go/No-Go判定、切り戻しの判断 〔判断者は未定義〕。移行結果の最終報告（主体） |

## 自分たちの役割（責任範囲）

| 自分たちがやる | 自分たちはやらない（判断を仰ぐ・任せる） |
|---|---|
| 確認者の指示に従った移行実行とログ格納 | 作業開始のタイミングの判断 → 確認者（センター） |
| エラーを見つけたら止めて、**原因と、作業の続行への影響を説明する**（下の「エラーが起きたときの報告」） | 致命的なエラーかどうかの判断 → センター |
| 判断に必要な材料を整理して渡す（状況・切り戻しの所要時間など） | Go/No-Go判定・切り戻しの判断 → センター |
| 作業者が説明できないときの連絡ルートを決めておく | |
| 指示があれば切り戻し作業を行う | 住記などの移行ツールの実行 → 移行チーム |
| 本番切替では、移行結果の最終確認を支援する（人を出す） | 移行結果の最終報告 → センター（主体） |

## エラーが起きたときの報告

判断はセンターが行う。そのために自分たちは、「エラーが出た」「エラーコードが何番だった」で終わらせず、**なぜ起きたのか、作業の続行にどう影響するのかを説明する**。

### 報告の2つの段階

| 段階 | 中身 | 誰ができる必要があるか |
|---|---|---|
| ① 事実 | 何が起きたか（下の表） | 作業者全員 |
| ② 原因と影響の説明 | なぜ起きたのか。作業の続行に問題があるのか、ないのか | 説明できる人。作業者ができなければ、連絡ルートで説明できる人につなぐ |

②の説明の例：

- 想定外の一意制約エラー：「○○という事前の事情が考慮できておらず、同じキーのデータが二重に入った。対象は○件で、××すれば解消できる」
- コンパイルエラー：「このスクリプトが不足している。ただし、今回の実施には使わない部分なので、作業の続行には問題ない」

### ① 事実として押さえること

| 項目 | 報告すること |
|---|---|
| いつ | 発生した時刻 |
| どこで | タイムチャートのどの工程か。どの移行ツール（バッチ）か |
| 何が | エラーの内容。ログの場所と該当行 |
| どこまで進んだか | 完了した工程と、終わっていない工程。データが途中まで取り込まれているか |
| 何をしたか | 発生する前の操作と、発生した後の操作（「何もしていない」も報告する） |
| 今の状態 | どこで止めているか。そのまま再実行できる状態か |

- ログは消さない・上書きしない。再実行する前に、必ず退避する。
- 推測を事実のように言わない。わからなければ「わからない」と言って、②の説明ができる人につなぐ。

### 連絡ルート 〔要決定：自チーム内で決める〕

作業者が②を説明できないときに、誰へ、どの手段でつなぐか。当日の体制表に書いておく。

- 作業者 → 自チーム内で説明できる人（誰か、当日いない場合の代わりは誰か）
- 説明できる人 → 確認者（センター）

現状（令和8年度）：現場リーダー等はチームリーダー。対象は1団体のみのため、これで回す。
令和9年度に向けて：連絡ルートだけでなく、連絡フロー（何があったら、誰が、何を持って、どうつなぐか）を自チーム内で決める。

## 流れ

1. **移行実行**：確認者の開始指示 → 抽出CSVの配置 → 移行ツール実行（一部は移行チーム） → ログ格納 → 確認者によるログ・件数の確認
2. **Go/No-Go判定**：判断材料を整理して渡す → 判定 → Go なら稼働、No-Go なら切り戻し（リハーサルでも同じ段取りで行う）
3. **移行結果の最終確認の支援**（本番切替のみ）：センターが主体で行う最終確認のために、自チームから人を出す。最終確認は、本確認の観点の一部を使う（詳しくは「移行結果の確認」） 〔要確認：支援の範囲〕

## 注意点

- **手順書にないことはしない**。時間が押していても、確認を省略して先へ進まない。遅れていると感じたら、すぐ確認者へ報告する。
- **リハーサルで出た課題は、すべて記録して「移行の準備」へ渡す**。小さなことでも、本番で同じことが起きる。
- **作業対象は本番環境**（リハーサルも同じ）。誤操作は、そのまま稼働に響く。作業前に、対象の環境を必ず確認する。
- **ミスに気づいたら、隠さずすぐ報告する**。リハーサルでは、作業ミスに気づいてやり直したことがある。早く気づいて報告すれば、取り返せる。
- **エラーの判断と切り戻しの判断は、自分でしない**。ただし、判断できるだけの説明は自分たちが出す。
