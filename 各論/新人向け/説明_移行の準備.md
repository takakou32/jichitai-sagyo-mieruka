# 説明：移行の準備（下書き）

> 〔要確認〕は推測で書いた箇所。直したら印を外す。

| 項目 | 内容 |
|---|---|
| 大きな枠 | 切替 |
| 目的 | 「移行の実施」で使う移行ツール・移行資産・手順書を、実行できる最新の状態にそろえる |
| 時期・頻度 | 随時。開発元のリリースや、リハーサルのたびに発生する 〔要確認：リリースの頻度〕 |
| きっかけ | 下の表のとおり |
| 完了の条件 | 次の「移行の実施」で使う移行ツール・資産・手順書が確定し、移行チームが使う移行ツールと版が一致している |

## きっかけの種類

| きっかけ | 中身 |
|---|---|
| 移行ツールのリリース | 開発元が移行ツールの新版を定期的にリリースする。アプリケーションのバージョンアップに伴うものと、移行仕様の修正によるものがある |
| リハーサルの課題 | 「移行の実施」（リハーサル）で出た課題を、手順書や資産に反映する |
| 移行仕様の変更 | 〔要確認：リリース以外で仕様が変わることがあるか〕 |

## 関わる人

| 誰が | 何をするか |
|---|---|
| 開発元 | 移行ツールの新版をリリースする |
| 自チーム | 新版のとりまとめ、カスタマイズとのマージ、テスト、資産・手順書の更新、移行チームへの共有 |
| 移行チーム | 共有された移行ツールを受け取り、本番切替の当日に住記などの移行ツールを実行する |
| センター | 〔要確認：承認や確認の手続きがあるか〕 |

## 流れ

1. **新版の受け取り**：開発元のリリースを受け取る。何が変わったか（アプリのバージョンアップに伴うものか、移行仕様の修正か）を確認する
2. **とりまとめ**：新版の資産を集め、GUI（iko_gui）にセットする（定型）
3. **カスタマイズとのマージ**：自分たちのカスタマイズと新版をマージする（判断）
4. **テスト**（定型）
5. **資産・手順書の更新**：リハーサルの課題もここで反映する（定型）
6. **移行チームへの共有**：当日、移行チームが使う移行ツールの版を、取り込んだ版と一致させる（調整）
7. **版の記録**：どの版を、いつ、どこに反映したかを記録する（定型）

## 注意点

- **移行チームと版を合わせる**。共有が漏れたり遅れたりすると、本番当日に移行チームが古い版を実行してしまう。
- **マージで自分たちのカスタマイズを消さない**。新版で上書きする前に、カスタマイズの差分を確認する。
- **手順書と資産の版を対応させる**。手順書がどの版の資産を前提にしているかを明記する。
- **リハーサルの課題の反映漏れに注意する**。課題一覧と突き合わせて、すべて反映したことを確認する。
