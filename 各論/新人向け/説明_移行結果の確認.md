# 説明：移行結果の確認（下書き）

> 〔要確認〕は推測で書いた箇所。直したら印を外す。

| 項目 | 内容 |
|---|---|
| 大きな枠 | 切替 |
| 目的 | 移行後のデータが現行環境のデータと合っていることを確かめ、自治体に出す移行結果報告資料（正式名称：データ移行仕様書兼データ移行・動作検証結果報告書）をまとめる |
| 時期・頻度 | 団体ごとに、本番稼働の前に3段階で行う（下の表） |
| きっかけ | ①年度の計画 ②稼働直前のリハーサルが終わる ③本番切替 〔要確認〕 |
| 完了の条件 | 確認観点ごとに、差異の有無と、差異があればその原因と影響を説明した報告資料ができている |

## 3つの段階

| 段階 | 時期 | 使うデータ | 自チームの関わり |
|---|---|---|---|
| ① R8年度中の移行結果報告資料の作成 | 稼働の前年度中 | これまでの移行データ | 自チームが行う |
| ② R9年度の稼働直前の移行結果報告資料の作成 | 稼働の年度、各団体の稼働前 | 稼働直前のリハーサルのデータ | 自チームが行う |
| ③ 最終確認 | 本番切替のとき | ②の観点の一部を使って最終報告 | 支援にとどまる（「移行の実施」の中で人を出す） |

- ①で、差異とその理由を洗い出しておく。②では、①と同じ差異は説明済みとして扱い、**新しく出た差異に力を割く**。
- 自チームの負荷の山は②。稼働する団体が多い年度は、切替スケジュールと同じ密度で②が重なる。①でどれだけ「理由のわかった差異」を積み上げられるかで、②の重さが決まる。

## 始める前にそろっていること

- 確認観点・比較対象・比較方法が決まっていること（確立済み）
- 比較に使うデータ（移行後のデータと、現行環境のデータ）がそろっていること
- 前の段階の結果（理由のわかった差異の一覧）が手元にあること

## 関わる人

| 誰が | 何をするか |
|---|---|
| 自チーム | 決まっている確認観点について、比較・分析・調査・報告資料の作成をすべて行う（①②） |
| センター | 最終確認と、自治体への最終報告の主体（③）。①②の移行結果報告資料も受け取り、取りまとめて自治体に提出する（ほぼそのまま渡ることが多い） |
| 開発担当・業務担当 | 差異の原因を判断するための業務知識を提供する。簡単なことは開発担当に、現状の実運用の確認は業務担当に聞く。内容によって使い分ける |
| 自治体 | 移行結果の報告を受ける |

## 自分たちの役割（責任範囲）

| 自分たちがやる | 自分たちはやらない |
|---|---|
| 決まっている確認観点での比較 | 自治体への最終報告 → センター 〔要確認〕 |
| 差異の分析と、原因の調査 | 確認観点そのものの追加・変更の決定 〔要確認〕 |
| 業務知識の収集 | |
| 報告資料の作成 | |
| ③最終確認の支援 | |

## 流れ（①②）

1. **比較**：決まっている観点・方法で、移行後のデータと現行環境のデータを比べる（定型）
2. **差異の抽出**：前の段階で理由がわかっている差異と、新しく出た差異を分ける（定型）
3. **差異の分析・原因の調査**：新しく出た差異について、なぜ起きたのか、業務への影響はあるのかを調べる（判断）
4. **業務知識の収集**：原因の判断に必要な業務知識を集める（調整）
5. **報告資料の作成**：確認観点ごとに結果をまとめる（定型）
6. **差異一覧の更新**：理由のわかった差異を記録し、次の段階に引き継ぐ（定型）

## 注意点

- **差異は「ある・ない」で終わらせない**。なぜ起きたのか、業務に影響があるのかまで説明する。「移行の実施」のエラー報告と同じ考え方。
- **事実と推測を分ける**。原因が確かめられていないものは、そう書く。
- **理由のわかった差異は必ず記録する**。次の段階と、ほかの団体の確認がそのぶん軽くなる。
- **想定外の差異は、ためこまずに早めに共有する**。稼働日から逆算すると、調査に使える時間は限られている。
