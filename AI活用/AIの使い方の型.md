# AIの使い方の型（たたき台）

> 〔要確認〕は推測。
> 道具（エージェントかチャットか）にも、モデルにも依存しない。違うのは、入力と出力を運ぶのがツールか人か、だけ。

AIを使う場面ごとに、次の「型」を1つ決めておく。

| 項目 | 決めること |
|---|---|
| 入力 | 何を渡すか |
| 指示 | 何を頼むか（共通の前置き＋この場面の依頼）。版の番号を付ける |
| 出力の形 | 何を、どの形で返させるか |
| 人の確認 | 人が何を確かめてから次へ進むか |
| 記録 | 何を残すか |

## 共通の部分（どの型でも使う）

**前置き（v0.1）**：最初に渡す。

```
自治体システム標準化の移行・保守作業を手伝ってください。
事実と推測を分け、根拠（ログの行、ソースの箇所、手順書の項目）を示してください。
材料が足りなければ、推測で埋めずに、足りないものを挙げてください。
判断が必要なことは、選択肢と影響を示して、人に委ねてください。
```

**渡してよいデータ（v0.1）**：現場の Copilot Chat は、エンタープライズデータ保護が効いている。

- 個人情報を含まなければ、業務の資料・ログ・ソースは渡してよい。
- 個人情報（住民の氏名・住所・生年月日・宛名番号など、個人を特定できる値）は渡さない。
- 住民データを扱うときは、値の代わりに、項目名・値の形（桁数・文字種・空かどうか）・件数を渡す。
- ログや画面の写しに個人情報が出ているときは、伏せてから渡す。伏せられないものは渡さない。
- 迷ったら渡さず、リーダーに聞く。

**記録**：会話の最後にAIにまとめさせ、人が「人の判断」を書き足して残す。

```
件名／日付／型と版／渡した材料／AIの答えの要点／人の判断（採用・修正・不採用と理由）
```

## A. トラブルシュート

| 項目 | 中身 |
|---|---|
| 入力 | 最低限は、事象の説明・ログ・ソースの3つ。集め方とそろわないときは下の表。**トラブル一覧**も必ず渡す |
| 指示 | 下の「依頼（A v0.1）」 |
| 出力の形 | 端的に。下の「出力の形」 |
| 人の確認 | 下の「確認」 |
| 記録 | 共通の記録。新しい型のトラブルなら、**トラブル一覧に追加する**（下の「トラブル一覧」） |

- トラブル一覧に載っていれば、AIを使わずにその説明で報告する。
- 本番切替・リハーサルの当日は、現場リーダー等への連絡を先にする 〔要確認〕

### 入力がそろわないとき

| そろったもの | 扱い |
|---|---|
| 事象の説明＋ログ＋ソース | そのまま使う |
| 事象の説明＋ログ（ソースがない） | 使う。ソースの代わりに、手順書・仕様書・過去の事例があれば渡す。「ソースはない」と明記して渡す |
| 事象の説明＋ソース（ログがない） | 使う。エラーメッセージや画面の表示を、事象の説明に書き写す |
| 事象の説明だけ | AIは使わない。現場リーダー等へ上げる |

- 事象の説明は必須。ほかがそろわなくても、これだけは書く。
- 足りないものは、足りないと明記して渡す。AIはそのぶん確度を下げて答える。
- ログが長いときは、エラーの前後を切り出して渡す（時刻も含める）。

### 材料の集め方

AIが判断できる材料を集めるのが、作業者の最初の頑張りどころ。システムは k8s 上の pod で動いているので、ログを集める前に押さえることが多い。

**まず退避する**：pod が再作成されると、そのログは消える。調べる前に、関係するログを手元に退避する。

| 押さえること | 確かめる内容 |
|---|---|
| どの pod か | どの業務・どの機能のエラーか。同じアプリの pod が複数あれば、すべてが対象 |
| いつか | 発生時刻と、その前後の範囲。ログの時刻が UTC か JST か |
| 再起動していないか | 再起動の回数。再起動していれば、再起動前のログ（`kubectl logs --previous`）も取る |
| pod の状態 | `kubectl describe pod` とイベント。メモリ不足で落ちた、起動の確認に失敗した、などがここに出る |
| どのコンテナか | pod に複数のコンテナがあれば、どれのログか |
| ログはどこにあるか | 標準出力か、コンテナ内のファイルか。DB側やバッチのログも要るか |
| 突き合わせの手がかり | 処理のID・団体・対象データなど、複数のログをつなぐもの |
| 直前に何をしたか | 直前のデプロイ、設定の変更、移行ツールの実行。環境バージョン一覧も見る |

現場固有の対応（業務ごとの namespace・pod・ログの場所など）は、`site/ログの場所.md` にまとめる 〔要確認〕

### 依頼（A v0.2）

```
添付の材料から、このエラーの原因と、作業の続行への影響を出してください。
- 材料：事象の説明、ログ、ソース、トラブル一覧（足りないものは「なし」と書いてある）
- トラブル一覧に同じ型のものがあれば、まずそれを示してください。
- 根拠は、ログの行・ソースの箇所で示してください。根拠を示せない見立ては書かないでください。
- 材料が足りず判断できないときは、推測で答えずに、必ず下の「材料が足りないとき」の形で返してください。
- 下の「出力の形」で、端的に答えてください。
```

### 出力の形

```
結論：（1行）
原因：（3行以内）
根拠：（ログの行・ソースの箇所を箇条書き。3つまで）
続行への影響：（問題なし／条件つきで続行可／続行不可）と、その理由を1行
確度：（高・中・低）
確かめ方：（人がすぐ確かめられる方法を1〜2個）
```

材料が足りないとき：

```
判断できません：材料が足りません。
足りないもの：（箇条書き）
取り直し方：（ログを取り直す範囲・時刻・対象など、わかる範囲で）
次にやること：上を集めてもう一度聞いてください。集められないときは、現場リーダー等に相談してください。
```

### 確認

AIの答えを、そのまま報告しない。次の順に確かめる。

| # | 確かめること | 誰 |
|---|---|---|
| 1 | 根拠に挙がったログの行・ソースの箇所が、実際にあるか。AIの説明と合っているか | 作業者 |
| 2 | 事象と食い違っていないか（時刻、対象、件数など） | 作業者 |
| 3 | 「確かめ方」を、すぐできるならやってみる | 作業者 |
| 4 | 原因と影響を判断する | 現場リーダー等 |

- 1〜3で食い違いがあれば、その結果を貼って、もう一度聞く。
- 確度が「低」、または影響が「続行不可」なら、1〜3の途中でも現場リーダー等へ上げる。
- 確かめられなかったことは、「未確認」と明記して報告する。

### 解決まで行けなかったとき

AIが「判断できない」と答えたときや、確認で食い違いが解けなかったとき。

| # | やること | 誰 |
|---|---|---|
| 1 | AIが挙げた「足りないもの」を集めて、もう一度聞く（もう一度までにする） | 作業者 |
| 2 | 集められない、または二度目でも判断できなければ、現場リーダー等へ上げる。渡すもの：事実、AIの見立て（確度つき）、足りないものと集められなかった理由 | 作業者 |
| 3 | 現場リーダー等でも判断できなければ、外へ問い合わせる（開発元、センターの開発担当・業務担当） | 現場リーダー等 |
| 4 | トラブル一覧に「未解決」で載せる。回答が来たら更新する | 作業者 |

- 本番切替・リハーサルの当日は、1を飛ばして2へ進む。判断はセンターなので、「わかっていること」と「わかっていないこと」を分けて伝える。
- 「判断できない」も立派な結果。何がわかっていないかがはっきりしていれば、判断する人は動ける。

### トラブル一覧

現場リーダー等が原因と影響を判断したら、新しい型のトラブルを1行追加する。次に同じことが起きたら、作業者がこの一覧で説明できるようにする。

| 項目 | 書くこと |
|---|---|
| 事象の型 | どんなときに、どんなエラーが出るか（値は一般化して書く） |
| 原因 | 3行以内 |
| 続行への影響 | 問題なし／条件つきで続行可／続行不可 |
| 対応 | どうすれば解消できるか |
| 確かめ方 | この型だと見分ける方法 |
| 状態 | 解決／暫定対応／未解決 |
| 初出 | 日付と、そのときの記録の件名 |

- 置き場所：`site/トラブル一覧.md` 〔要確認〕

## B. 新人の質問

| 項目 | 中身 |
|---|---|
| 入力 | `引き継ぎ.md`、`全体まとめ.html`、該当するイベントの新人向けの説明（`各論\新人向け\`） |
| 指示 | 資料に書いてあることだけで答えて。なければ「資料にない」と答えて |
| 出力の形 | 答えと、資料の箇所 |
| 人の確認 | 「資料にない」ことだけリーダーに聞く |
| 記録 | 聞いた答えを資料に書き足す |

## C. ツールの小さな修正

| 項目 | 中身 |
|---|---|
| 入力 | 症状（エラーメッセージ、期待した動きと実際の動き）、関係する関数やファイルだけ |
| 指示 | まず原因を説明して。合意したら、直したファイルを全体で出して |
| 出力の形 | 原因の説明 → 直したファイル → 確かめ方 |
| 人の確認 | 差分を見て、実行して確かめる |
| 記録 | 共通の記録。コミットのメッセージに要点を書く |

- 外（自社端末）で作ったツールを直したときは、何を直したかを、値を伏せた言葉で外に伝える。

## E. 手順書の反映もれの点検（移行の準備 A2）

| 項目 | 中身 |
|---|---|
| 入力 | 前回の課題一覧（ボードから書き出したもの）、団体ごとの差分の一覧、更新した手順書（Word）。個人情報は含まれないので、そのまま添付してよい |
| 指示 | 下の「依頼（E v0.1）」 |
| 出力の形 | 課題・差分1件ごとに1行の表 |
| 人の確認 | 「未反映」「判断できない」の行を、手順書で確かめる |
| 記録 | 共通の記録。未反映を直したら、ボードの課題を更新する |

### Copilot Chat での進め方

1. Copilot Chat で新しいチャットを開く。
2. 共通の前置きと、下の依頼文を貼る。
3. 3つのファイルを添付して送る。手順書が長いときは、章ごとに分けて頼む（長いと読み落としが出やすいため）。
4. 返ってきた表を Excel に貼り、「未反映」「判断できない」の行だけを手順書で確かめる。

### 依頼（E v0.1）

```
添付の「前回の課題一覧」と「団体ごとの差分の一覧」の内容が、添付の手順書に反映されているかを点検してください。
- 課題・差分を1件ずつ、手順書のどの章・手順番号に反映されているかを示してください。
- 手順書の該当する文を、短く引用してください。
- 見つからないもの、反映されているか判断できないものは「未反映」「判断できない」としてください。推測で「反映済み」にしないでください。
- 最後に、未反映と判断できないものの件数を書いてください。
```

### 出力の形

```
| No | 課題・差分（要約） | 出どころ（課題一覧／差分一覧） | 判定（反映済み／未反映／判断できない） | 手順書の箇所 | 引用 |
```

### 確認

| # | 確かめること | 誰 |
|---|---|---|
| 1 | 「未反映」「判断できない」の行を、手順書で確かめる。本当に漏れていれば直す | 作業者 |
| 2 | 「反映済み」の行は、引用が課題の意図と合っているかを数件だけ抜き取りで見る | 作業者 |
| 3 | 直しきれないもの、判断に迷うものは、確定の前にリーダーに上げる | 作業者 |
